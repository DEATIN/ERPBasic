# Документы, роли и границы доступа

## Карта документов

| Интерфейс / операция | Native DocType | Учётный результат при проведении |
|---|---|---|
| Предложение | Quotation | Коммерческие условия; без склада и начисленной задолженности |
| Заказ покупателя | Sales Order | Обязательство исполнения и штатные показатели заказа; без отгрузки и дебиторской задолженности |
| Отгрузка | Delivery Note | Физическое движение и стоимость запасов |
| Счёт покупателю | Sales Invoice | Начисление и расчёты с покупателем; в связанной цепочке `update_stock=0` |
| Заказ поставщику | Purchase Order | Обязательство закупки; без физической приёмки |
| Приёмка | Purchase Receipt | Поступление запасов и native связь с закупкой |
| Счёт поставщика / расходная услуга | Purchase Invoice | Обязательство перед поставщиком и расход; отдельная Payment Entry подтверждает оплату |
| Получение, выплата, аванс | Payment Entry | Движение по денежному счёту и распределение на native основания |
| Перемещение / списание / поступление | Stock Entry | Native складские движения по выбранному purpose |
| Инвентаризация / начальный запас | Stock Reconciliation | Согласование количества и стоимости по складу |
| Начальные проверенные расчёты | Journal Entry, Opening Entry | Срез дебиторской/кредиторской задолженности, авансов и денег; не фиктивный банковский платёж |
| Организация, склад, справочники | Company, Warehouse, Item, Customer, Supplier, UOM, Contact, Address | Штатные объекты ERPNext |

«Реализация» браузерной демонстрации объединяла экономически разные факты. На сервере это цепочка отгрузки и счёта; создание «на основании» сохраняет native ссылки строк. Изменение количества в частичной приёмке сохраняет ссылку на заказ и передаёт пересчёт Received/Accepted штатному контроллеру.

## Состояния и ошибки

Учётный документ проходит `Draft (docstatus=0) → Submitted (1) → Cancelled (2)`. Native статус исполнения и `docstatus` — разные поля. Basic не разрешает сохранить проведённый документ как черновик. Для корректировки используются отмена/новый документ или native возврат; ссылочные ограничения ERPNext сохраняются.

Каждое сохранение/проведение/отмена и создание связанного документа требует ключ команды. Изменение имеющегося документа дополнительно требует `expected_modified`. При конфликте интерфейс загружает актуальные данные. При потере ответа он сохраняет один незавершённый запрос в `sessionStorage` и предлагает повторить точное тело с прежним ключом; это временное состояние транспорта, не локальная учётная база.

Ошибка после начала проведения не подтверждает успех. Frappe откатывает запрос целиком. Native сообщения о недостатке товара, закрытом периоде, недостающем счёте или обязательном реквизите не превращаются в успешное состояние UI. Подробности о backdated repost и сложных учётных настройках смотрите в штатном ERPNext Desk администратора.

## Роли

Профиль задаёт стандартные роли; эффективные read/create/write/submit/cancel/import/export вычисляет сервер, а не эта справочная таблица.

| Профиль `staff.invite` | Назначаемые основные роли | Назначение |
|---|---|---|
| `owner` | System Manager, Sales/Purchase/Stock/Accounts Manager | Владелец всего Site и учётных настроек |
| `administrator` | System Manager | Пользователи, конфигурация и полный административный Desk |
| `sales` | Sales User | Покупатели и продажи в разрешённых Company |
| `purchasing` | Purchase User | Поставщики и закупки |
| `warehouse` | Stock User | Складские документы в пределах native разрешений |
| `finance` | Accounts User | Счета, оплаты и взаиморасчёты |
| `observer` | ERP Basic Observer | Чтение основных документов; без проведения, изменения и экспорта |
| `integration` | ERP Basic Integration, Sales User | Отдельный API-пользователь connector, ограниченный Company |

Каждому профилю добавляется `ERP Basic User`. Для просмотра бизнес-аудита нужна отдельная `ERP Basic Audit Reader` либо System Manager. Интеграционный пользователь не может быть System Manager. Административные роли дают весь Site: ими нельзя моделировать менеджера одной Company.

Роль `ERP Basic Integration` дополнительно запрещает проведение и отмену учётных
документов через native permission hook, даже если стандартная Sales User иначе
дала бы такое право. Импорт CRM создаёт черновик; его проводит отдельный сотрудник.
Для возврата результатов этой роли назначено только чтение Sales Invoice и Payment Entry;
запись и проведение финансовых документов ей не предоставляются.
Её HTTP-запись ограничена контрактом `erp_basic.integration.*`: общий endpoint сохранения
не позволяет обойти владение полями и контроль версии входящего сообщения. Ограничение
служебной учётной записи сохраняется и после включения полного режима Site.

Сотруднику создаётся стандартный User с письмом установки собственного пароля; общих паролей нет. Почтовый транспорт настраивается оператором. `staff.disable` блокирует пользователя и завершает его сессии; `staff.end_sessions` позволяет закончить свои сессии или администратору — сессии сотрудника. Frappe обеспечивает cookie/CSRF, password policy и ограничение повторов входа. Первичный Administrator создаётся `bench new-site` со случайным индивидуальным секретом.

## Проверяемые пути

| Путь | Контроль |
|---|---|
| Команды `erp_basic.api.*` | Аутентификация, Company, native роль, документ, версия, allowlist полей и устойчивый ключ |
| Повтор сохранённой команды | Текущая роль и Company проверяются заново, включая право чтения результата |
| Списки/поиск/CSV | Серверный фильтр Company, native `get_list`, страницы 1–100; export дополнительно требует native export permission |
| Стандартный REST | Для обычного Basic-пользователя только чтение известных ресурсов; Company hooks, запрет document RPC и неограниченного размера страницы |
| Отчёты | В Basic используются `stock_balance` и `ledger` с явным Company; произвольные report RPC закрыты |
| Приватный файл | Native permission и дополнительная проверка родителя; upload учётного вложения требует private=1 |
| Фоновые задачи обмена | Настроенный connector, активный service user, область Company и текущие права |
| Миграция / приглашение / конфигурация | Только администратор Site; исходник и параметры проверяются на сервере |

Внешние идентификаторы не разрешают доступ. Нельзя подменить Company, связать склад/счёт другой организации или записать `grand_total`, `docstatus`, `flags` через форму Basic. Существующие поля child rows, которые не показаны в интерфейсе, сохраняются на сервере; пользователь не может присвоить строку другого документа.

## Аудит

`ERP Basic Audit Event` хранит автора, Company, документ, действие, время, request id и ограниченные before/after snapshots значимых сумм/строк/распределений. Пароли, API tokens и полные контактные карточки не копируются. Обычные пользователи не могут создавать, исправлять, переименовывать и удалять события. Внутренняя вставка аудита — узкое исключение `ignore_permissions`; пользовательские документы всегда используют обычные права.

Native Version дополняет аудит там, где включён `track_changes`. Технические исключения и отклонённые запросы находятся в диагностике Frappe; они не выдаются за успешно совершённые бизнес-операции. Журнал обмена отдельно показывает доставку и конфликты. Доступ оператора к самой БД и файловой системе находится за пределами прикладного запрета изменения аудита.

Аудит охватывает учётные документы, Item/Customer/Supplier и Warehouse, включая штатное
`on_update_after_submit`. Контур определяется изолированной БД Site; Company хранится
в событии. Общие справочники Site имеют пустую Company. Администрирование User/Role и
конфигурации остаётся в штатной истории и диагностике Frappe; журнал Basic не заявляется
полным аудитом всех административных действий платформы.
