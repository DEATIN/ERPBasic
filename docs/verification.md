# Проверки серверной основы

Этот отчёт различает проверки настоящей учётной системы, контрактные проверки интерфейса
и ещё не выполненные эксплуатационные испытания. Начальный машинный отчёт сохранён в
[infra/validation-initial.json](../infra/validation-initial.json); финальные GitHub Actions
и companion PR Clientora дополняются по завершении проверки текущего commit.

## Окружение

Первый стенд использовал MariaDB 10.6.24, но эта серия уже завершила Community-поддержку.
Повторная чистая установка и полный прогон выполнены на **MariaDB 10.11.19,
READ-COMMITTED, Redis 7.2.17, PostgreSQL 17.11**, Python 3.12.14, Node 24.22.1,
Frappe 15.126.0 и ERPNext 15.124.5. Точные версии/commit/checksum закреплены в
[infra/versions.json](../infra/versions.json). Frappe 15 предупреждает о MariaDB >=10.9;
проверены перечисленные сценарии, а не вся upstream suite ERPNext.

Базы данных, HTTP-процессы и worker настоящие, с отдельными подключениями. В CI они
создаются заново. Кэш загрузок может переиспользоваться после проверки checksum;
он не заменяет новую БД или повторную установку схемы.

## Учётные и защитные сценарии

| Набор | Подтверждённый результат |
|---|---|
| `test_core.run` | 9 бизнес-сценариев: продажи/закупки, оплата, возврат, складская стоимость, запрет подмены и аудит |
| `test_concurrency.run` | 4 сценария с независимыми процессами/DB connections: одинаковые ключи, разные ключи одного документа, конкурирующие списания и потерянный ответ после commit |
| `test_migration.run` | 5 проверок dry run, ссылок/дублей, начального запаса, повторного импорта, подтверждённого финансового среза и общей модели полного ERPNext |
| `test_http` | Настоящие login/CSRF/logout, сохранение/проведение/повтор, Company/роль, стандартный REST, приватный файл и доступность `/erp` с assets |
| `test_http_tenant` | 3 HTTP-сценария двух отдельных Sites/БД с одинаковыми Company и логином: SID, документы/списки/файл, native SLE/отчёт |
| `test_integration.run` | Настоящие native Sales Order, ERP-цены, атомарность inbox, конфликты содержимого и версий, отозванные права и управляемый повтор |
| Проверка RQ | Задание действительно исполняется отдельным worker через Redis |

В частности:

- Приходы **10 × 100 + 10 × 200 = 20 единиц, стоимость 3 000**; отгрузка 4 списывает
  600, остаётся **16 единиц стоимостью 2 400**. Возврат восстанавливает 20/3 000.
- Связанный Sales Invoice не создаёт второе складское списание. Payment Entry на 600
  по счёту 1 200 оставляет начисленный долг 600.
- Частичная закупка 4 из 10 сохраняет native ссылку на PO; Purchase Invoice не дублирует
  приёмку, возврат поставщику согласует количество и стоимость.
- Перемещение, списание, инвентаризация и её отмена сверяются по native Bin/SLE.
  Упаковка по 5 переводится в stock UOM; повторяющиеся строки учитываются вместе.
- При остатке 5 два независимых процесса пытаются списать по 4: проходит один,
  остаток равен 1. Несколько одновременных submit одного документа дают один результат.
- Искусственно вызванная ошибка после реальной записи SLE откатывает документ,
  движения и результат команды в одной транзакции.
- Повтор ключа с другим телом даёт конфликт; новый ключ не перепроводит Submitted.
  Сохранённый ответ не отменяет повторную проверку текущих прав.
- Подмена Company, склада другой Company, итоговой суммы и системных полей отклоняется.
  Обычный Basic-пользователь не может обойти шлюз через native resource POST/PUT/DELETE
  или `GET ?run_method=submit`.
- Отдельный integration user с Sales User и Company получает 403 на общий save
  нового/существующего документа и submit. Успешный импорт CRM остаётся черновиком;
  проведение принадлежит сотруднику ERP.

На втором чистом Site проверена первичная `create_company`: создана одна Company,
83 Account, 5 Warehouse, 2 Cost Center, 1 Fiscal Year и 6 Item Group. Повтор не добавляет
строк. Это проверка стандартного стартового плана, а не настройка российского
регламентированного учёта.

Изоляция Site проверена при одинаковых названиях Company и логине в двух базах:
SID первой площадки не аутентифицирует во второй; документ и приватное вложение первой
не выдаются второй; реальное движение SLE первой не появляется в ledger второй.

## Настоящий обмен Clientora ↔ ERP

Companion-код Clientora проверен с PostgreSQL 17.11; ERP работает на MariaDB.
Сквозной тест запускает **два настоящих HTTP-сервера** и использует фактический обработчик
создания заказа Clientora. На поддерживаемом профиле 6 проверок прошли за 6,86 секунды:

1. CRM создаёт заказ и outbox в одной транзакции, затем доставляет native Sales Order в ERP.
2. Уполномоченный пользователь ERP проводит заказ, outbox возвращает `docstatus=1` в CRM.
3. Повтор UUID не создаёт второй документ; другое содержимое того же UUID даёт конфликт.
4. Устаревшее событие ERP не затирает более новую проекцию Clientora.
5. HTTP-ответ намеренно теряется после фиксации на сервере; повтор доставляет сохранённый результат.
6. Нет циклических событий и выдуманных финансовых фактов по CRM-статусу оплаты.

Цена берётся из ERP Item Price, а не из произвольного CRM payload. Названия, телефоны
и email не используются как единственные технические ID. Реальный callback, устойчивые
lease и повтор при недоступном HTTP дополнительно проверены в Clientora на PostgreSQL.

## Миграция и восстановление

Фактический демо-набор JSON v2 содержит 31 исходную запись. Контрольный перенос даёт
**99 единиц и стоимость 62 340**, сохраняет карту ID, связи и исходную историю в архиве.
Повтор не добавляет запас. Отдельная подтверждённая тестовая дебиторская задолженность
1 000 переносится native opening Journal Entry. Демо-оплаты не считаются подтверждением
банка; без финансового среза отчёт явно отмечает `stock_only_financial_pending`.

Расширение Basic → полный ERPNext проверяет сохранение ID и SLE тех же native документов.
Это не испытание производства, всех новых ролей или всех модулей ERPNext.

Зашифрованная полная копия восстановлена в новый Site и новую БД на том же MariaDB instance.
Сверены 91 тип документов/дочерних таблиц, публичные и приватные файлы, а также фактическая
расшифровка сохранённого Password. Восстановленный контур имеет maintenance,
отключённый scheduler/email и запрещённые внешние вызовы; коннекторы не отправляют очередь.
Начальный полный прогон занял 148,664 секунды, импорт/проверка восстановления — 7,506 секунды.
Эти измерения относятся к небольшому тестовому набору и уже подготовленному узлу;
они **не являются гарантией рабочего RTO**. Политика RPO/RTO и отдельного хранения —
в [инструкции восстановления](../infra/README.md).

## Интерфейс и воспроизведение

```bash
npm run проверка
npm run тесты
python3 инструменты/синхронизация-стилей.py --check
```

Node выполняет **38 тестов**: существующие 7 тестов демо и 31 проверку
server-api/server-startup. HTTP
проверяется отдельно против реального ERPNext. Chromium workflow использует явно
описанные HTTP-фикстуры для экранов, тем, мобильного вида и восстановления запросов;
результат такой проверки нельзя выдавать за сквозное проведение через настоящую БД.

Контрактный Chromium-прогон 9/9 успешно выполнен в
[GitHub Actions на commit 84b4b1e6](https://github.com/DEATIN/ERPBasic/actions/runs/42133886694).
Снимки светлой/тёмной тем и мобильного вида находятся в artifact `server-interface-contract`.
Отдельный `server-live.test.cjs` подключён к серверному CI через обязательный
`--browser-tests`: он не подменяет HTTP и после UI-проведения вызывает независимую
SQL-проверку сохранённого документа. Фактический результат этого нового прогона
добавляется после завершения CI.

Полный серверный прогон:

```bash
"$ERP_RUNTIME_DIR/bench/env/bin/python" инструменты/сервер/ci.py \
  --root "$ERP_RUNTIME_DIR" --site ci.erp-basic.localhost
```

Нужен подготовленный по [инструкции](../infra/README.md) новый runtime без другого
supervisor на его портах. Тесты допускаются только в Site с `allow_tests=1`.

## Границы результата

Не объявлены выполненными: production-развёртывание, TLS и рабочий SMTP, удалённое
хранилище/планировщик/оповещения backup, восстановление всего узла под рабочей нагрузкой,
сертификация регламентированного учёта, банковский импорт, партии/серийные номера,
массовая переоценка задним числом и включение всех модулей ERPNext. Резервы отображаются
из ядра; отдельная команда физического резервирования в упрощённый UI не добавлена.
Новые направления интеграции требуют явного владельца полей и своих проверок.
