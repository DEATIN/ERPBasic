# Контрольная миграция JSON v2

Перенос выполняет администратор в отдельном тестовом Site. Поддерживается JSON, который экспортирует нынешняя демонстрация с `schema: 2`. Более старые отдельные browser-ключи `erp-records`/`erp-items` сначала преобразуются самой демонстрацией в v2; произвольный JSON без версии отвергается.

## Почему начальный срез

В исходнике есть конечные `items.qty`/`items.cost`, проценты исполнения заказа, демонстрационные оплаты и история интерфейса. Эти данные не доказывают даты всех движений, распределение по складам или подтверждение банка. Автоматическое воспроизведение такой истории вместе с конечным остатком удвоило бы учёт.

Выбранная стратегия:

1. Создать native Item/Customer/Supplier, цены, имеющиеся контакты и адреса.
2. Записать конечные количества и стоимость одним Stock Reconciliation с purpose `Opening Stock` на явно выбранный склад.
3. Перенести исходные черновики Quotation/Sales Order/Purchase Order в native черновики.
4. Сохранить **каждую** исходную запись, старое состояние, ссылки, history и хеш в неизменяемом архиве и карте идентификаторов. Проведённые demo документы не становятся заново проведёнными native документами.
5. При наличии проверенного финансового среза создать native opening Journal Entry для задолженности, авансов и денег. Демо-статус оплаты и формула «заказ − оплаты» не используются как доказательство финансового факта.

`reserved` сохраняется в архиве для сверки. Для создания действующих заказов на открытый остаток необходимо установить оставшиеся строки/количества; одного процента исполнения для этого недостаточно. Без проверенного финансового среза отчёт явно содержит `accounting_scope=stock_only_financial_pending`.

## Dry run

POST `/api/method/erp_basic.migration.plan`, cookie+CSRF либо native API token администратора. JSON-параметры:

```json
{
  "payload": {"schema": 2, "company": "...", "items": [], "customers": [], "suppliers": [], "orders": [], "quotes": [], "invoices": [], "purchaseOrders": [], "receipts": [], "stockDocs": [], "payments": [], "expenses": []},
  "company": "Моя компания",
  "warehouse": "Основной склад - МК",
  "source_id": "browser-export-2026-11",
  "cutoff_date": "2026-11-05",
  "uom_mapping": {"шт.": "Nos", "компл.": "Set", "усл.": "Nos", "час": "Hour"}
}
```

Укажите настоящий полный экспорт в `payload`. `source_id` обозначает источник и остаётся постоянным при повторе. Dry run не создаёт записи. Он проверяет версию, типы, id/дубли, ссылки, цены/количества, единицы, Company/склад и финансовый срез; возвращает `valid`, `errors`, `warnings`, количества, ожидаемые остатки/стоимость и детерминированный `run_id`.

Пример отдельно проверенного финансового среза:

```json
{
  "reviewed": true,
  "currency": "RUB",
  "entries": [
    {"kind": "receivable", "party_id": "C-001", "amount": "1000.00"},
    {"kind": "customer_advance", "party_id": "C-002", "amount": "200.00"},
    {"kind": "payable", "party_id": "S-001", "amount": "300.00"},
    {"kind": "supplier_advance", "party_id": "S-002", "amount": "50.00"},
    {"kind": "cash", "amount": "100.00"}
  ]
}
```

Это пример контракта, а не рассчитанные долги демонстрации. Для банковского остатка можно указать `kind=bank` и native `account` своей Company. Срез должен быть в валюте Company. Контрагенты разрешаются через старые id; названия, телефон и email не являются техническими ключами.

## Применение и повтор

POST `/api/method/erp_basic.migration.apply` с теми же параметрами, `plan_hash=<run_id>` и `accept_warnings=1`. Перед этим изучите полный dry run, обеспечьте отсутствие записей в тестовый срез и сделайте полную резервную копию. Принятие предупреждений явно подтверждает выбранный склад, архивную судьбу истории и необходимость финансовой сверки.

Сервис блокирует Company и выполняет весь перенос одной транзакцией. Ошибка не оставляет половину справочников или движений. Повтор того же `run_id` возвращает сохранённый отчёт; контрольные количества всех таблиц остаются прежними. Другой JSON под уже использованным `source_id` отклоняется: начальный срез не применяется повторно поверх первого. Для новой репетиции используйте восстановленный чистый Site.

Карта содержит старый id, тип источника, имя архивной записи и native DocType/name там, где объект действительно создан. Администратор может получить исходник через `migration.archive(company, mapping_name)`. Старые документы без достоверного учётного эффекта имеют архивный id, а не фиктивный номер проведённого ERP-документа.

## Сверка и проверенный результат

После импорта сверяются native Bin по Item/warehouse, количество, стоимость и исходный checksum. Есть отдельные проверки финансового opening GL, количества архивных записей, сохранности JSON/history и отсутствия дублей при повторе. Расхождение запасов откатывает перенос.

Контрольный набор получен непосредственно из `dist/assets/app.js` командой `node инструменты/демо-набор.cjs` и сохранён в `erp_basic/tests/fixtures/demo_v2.json`. Его фактическая проверка: 31 исходная запись, 99 единиц запасов, стоимость 62 340; повтор не увеличивает таблицы; отдельный тестовый подтверждённый receivable 1 000 отражается в GL. Скрипт проверки: `bench --site <test-site> execute erp_basic.tests.test_migration.run`.

Проверка расширения Basic открывает тот же Stock Reconciliation штатным ERPNext и сравнивает ID и записи SLE до/после. Включение полного интерфейса не выполняет вторую миграцию. Для production включения дополнительных модулей необходима проверка их собственных настроек и ролей.

## Откат

Контрольная миграция проводится в отдельном Site; откат репетиции — восстановление полного согласованного комплекта в новый изолированный Site. Не удаляйте GL/SLE SQL-командами и не удаляйте архив миграции для повторного импорта. После начала новых операций откат отдельного opening-среза требует анализа зависимостей и штатных отмен, а не возврата одного JSON.
