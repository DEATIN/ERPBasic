# Обмен с Clientora

ERP Basic реализует двусторонний обмен через постоянные входящие и исходящие журналы. Clientora передаёт предложение заказа; ERPNext создаёт или обновляет стандартный **черновик Sales Order**, рассчитывает его по собственным правилам и возвращает учётное состояние. Проведение выполняет отдельный сотрудник с соответствующими правами. События связанных Sales Invoice, Delivery Note и Payment Entry возвращаются в Clientora как отдельная учётная проекция.

Код ERP находится в `erp_basic/integration.py`, четыре DocType — в `erp_basic/erp_basic/doctype/erp_basic_*`. Для настоящего обмена нужен отдельный companion-коннектор в репозитории Clientora. Встраиваемая демонстрационная страница сама по себе коннектором не является.

## Контуры и владельцы данных

Один независимый клиент ERP Basic использует отдельный Frappe Site с отдельной БД. Company — организация внутри этого Site, а не замена изоляции клиентов. Подключение связывает ровно одну Company с одним UUID Organization из Clientora. После создания подключения эту связь изменить нельзя.

| Данные | Источник и разрешённые изменения |
| --- | --- |
| Организация Clientora, филиалы, контакты, расписание, операционный статус заказа | Clientora. Обратный учётный ответ не изменяет эти поля. |
| Company, Customer и его учётные реквизиты | ERP. Импорт заказа использует существующий Customer по явному соответствию; не создаёт и не переписывает реквизиты по имени, телефону или адресу. |
| Offering Clientora → Item ERP | Администратор настраивает соответствие UUID → native Item. Автоматического сопоставления по наименованию нет. |
| Предложение заказа | Clientora передаёт UUID клиента, UUID позиций, количество, валюту и дату исполнения. Для обновления ERP проверяет сохранённую ревизию черновика. |
| Цены, налоги, скидки, итоговые суммы | ERPNext. `quoted_total_minor` Clientora — справочная предложенная сумма; она не становится `rate` или `grand_total`. |
| Проведение, отмена, поставки, счета, оплаты, остатки и стоимость | Стандартные документы и контроллеры ERPNext. Статусы Clientora и Clientora Pro не создают финансовые или складские факты. |
| Учётный результат в Clientora | Отдельная проекция нативных документов ERP; она не записывает CRM Ledger и не меняет операционный статус заказа. |

При включении полного ERPNext сохраняются те же Company, Customer, Item, Sales Order и последующие документы. Таблицы журнала обмена дополняют стандартные документы; отдельного скопированного ядра ERP нет.

### Матрица владения и разрешения конфликтов

Внешний идентификатор задаёт стабильную связь объектов, а не разрешение изменять любые поля. «Не синхронизируется» означает отсутствие автоматической записи на другой стороне.

| Объект / значимые поля | Владелец | Кто создаёт / изменяет | Направление | Внешний ID | Правило конфликта |
| --- | --- | --- | --- | --- | --- |
| Organization: название, профиль, команда | Clientora | Владелец и уполномоченные участники CRM | Не синхронизируется; UUID задаёт контур | Organization UUID → Connector.source_tenant | Чужой UUID/токен отклоняется; ERP не создаёт Organization. |
| Company: учётная организация, валюта, счета по умолчанию | ERP | Администратор / разрешённый сотрудник ERP | Не синхронизируется; Company проверяется в сообщениях | Connector.company + local_tenant | Company/контур существующего подключения неизменяемы; несовпадение запрещает обработку. |
| Branch: филиал, часовой пояс, ресурсы | Clientora | Участник CRM с правами филиала | branch_id передаётся справочно; соответствия складу/Cost Center нет | Branch UUID в payload; отдельного mapping нет | Филиал не выбирает Company, Warehouse или счёт ERP и не создаёт учётный объект. |
| Customer Clientora: имя для общения, операционные сведения и контакты | Clientora | Уполномоченный пользователь CRM | Справочник не синхронизируется; в заказе только ссылка | Customer UUID → mapping customer | Только явное соответствие; совпадение имени/телефона не объединяет клиентов. |
| Customer ERP: учётное наименование, налоговые/платёжные реквизиты, группа | ERP | Сотрудник с native правами Customer | Не синхронизируется; заказ использует существующий Customer | Mapping Customer UUID → Customer.name | Proposal и callback не переписывают реквизиты; права на Customer проверяются. |
| Contact / Address CRM: контакты и адреса обслуживания | Clientora | Уполномоченный пользователь CRM | Не синхронизируется | Внешнего mapping в v1 нет | CRM контакт не меняет учётный адрес/контакт ERP. |
| Contact / Address ERP: учётный/юридический адрес и контакт контрагента | ERP | Сотрудник с native правами ERP | Не синхронизируется | Native имена; внешнего mapping нет | Поля ERP сохраняются; до автоматической записи нужен отдельный контракт. |
| Supplier: поставщик и реквизиты | ERP | Уполномоченный сотрудник ERP | Не синхронизируется | Native Supplier.name; внешнего mapping нет | CRM не создаёт/обновляет поставщиков и закупочные документы. |
| Offering: каталог CRM и предложение цены | Clientora | Уполномоченный пользователь CRM | UUID и количество → ERP; цена CRM справочно | Offering UUID → mapping offering | Без Item mapping — Needs Mapping; предложенная цена не заменяет цену ERP. |
| Item / UOM / Item Price: номенклатура, единица, коэффициенты, прайс | ERP | Уполномоченный сотрудник ERP | Справочники не синхронизируются; native правила применяются к заказу | Offering UUID → Item.item_code; UOM отдельно не сопоставляется | Вход не разрешает замену UOM, коэффициента или rate; ошибку native проверки исправляют в исходных настройках. |
| Sales Order: клиент, строки, количества, валюта, дата | ERP владеет документом; CRM — предложением | CRM предлагает; integration сохраняет черновик; сотрудник ERP проверяет | CRM → ERP, затем состояние ERP → CRM | Order UUID → mapping order → Sales Order.name | UUID/версия/хеш + сохранённая native modified; ручное изменение вызывает Conflict, проведённый документ защищён. |
| Статус работы CRM / выполнение Clientora Pro | Clientora / сервис Pro | Сотрудник или уполномоченный процесс CRM/Pro | CRM статус справочно → ERP; Pro не синхронизируется | Order UUID; Pro mapping в v1 нет | Статус не проводит/отменяет заказ и не подтверждает поставку/оплату. |
| Warehouse, остатки, стоимость и резервы | ERPNext | Native складские документы и разрешённые сотрудники | Полный складской баланс/резервы не синхронизируются; Delivery Note возвращает своё состояние | Native Warehouse / stock records; связанная Delivery Note.name | Числа CRM не перезаписывают остатки/оценку; конфликт резерва не решается временем сообщения. |
| Sales Invoice / Delivery Note: проведение, отмена, суммы, исполнение | ERPNext | Сотрудник / разрешённый native процесс ERP | ERP → учётная проекция CRM | Order UUID + erp_doctype:erp_name | Native read перед отправкой; версия отдельно по документу, старый снимок его не переписывает. |
| Payment Entry: подтверждённое поступление/списание и назначение | ERP | Сотрудник по подтверждению банка/кассы или настроенный учётный процесс ERP | ERP → проекция; CRM paid → платёж отсутствует | Order UUID + Payment Entry.name | Только native проведение меняет docstatus; callback не создаёт CRM Ledger или второй платёж. |
| Долг, авансы и взаиморасчёты | ERPNext | Расчёт из native счетов, платежей и распределений | Отдельные native суммы счёта/платежа → проекция; общий баланс/аванс отдельно не синхронизируется | Имена соответствующих Sales Invoice / Payment Entry | CRM не присылает авторитетный долг/аванс; значения не суммируются повторно по доставленным событиям. |

Подтверждение оплаты исходит от сотрудника, банка или кассы в учётном процессе ERP. Флаг paid, завершённая работа или успешная доставка сообщения в Clientora сами по себе таким подтверждением не являются.

## Первоначальная настройка

1. Установите приложения и выполните `bench --site <site> migrate`. В Clientora примените миграцию `0084_erp_basic_exchange` штатной командой `python manage.py migrate`.
2. Создайте отдельного активного **System User** в ERP с ролями `ERP Basic User`, `ERP Basic Integration`, `Sales User`. Задайте обязательное **User Permission: Company** на нужную организацию с применением ко всем DocType. Не назначайте `System Manager` и не используйте `Administrator` для обмена.
3. Создайте Frappe API key/secret для этого пользователя. Приложение добавляет роли `ERP Basic Integration` только **read** для Sales Invoice и Payment Entry; стандартный Sales User обеспечивает нужный доступ к заказу и накладной. Прав create/write/submit/cancel на эти финансовые документы не добавляется. При необходимости дополнительно ограничьте Customer и Item через native User Permissions.
4. Администратор ERP создаёт **ERP Basic Connector**. `source_system=clientora`, `source_tenant` — UUID организации Clientora, `company` — точное имя Company, `integration_user` — служебный пользователь. `local_tenant` создаётся автоматически: это стабильный UUID данного ERP-контура. При необходимости выберите активный прайс-лист продаж `selling_price_list`. Без него действуют стандартные настройки прайс-листа ERPNext.
5. Создайте независимый случайный ключ callback Clientora длиной не менее 32 символов. В ERP сохраните его в Password-поле `remote_token`, а `endpoint` задайте как `https://<clientora-host>/integrations/erp/v1/events/<clientora-org-uuid>`.
6. Владелец организации Clientora настраивает существующий Integration с provider `erp_basic` через `POST /api/erp-exchange/configure`: endpoint ERP — `https://<erp-site>/api/method/erp_basic.integration.receive`; `config.source_tenant` — **ERP Connector.local_tenant**, `config.company` — точное имя Company. В `credentials` передаются Frappe `api_key`, `api_secret` и отдельный `callback_token`. Ключи шифруются штатным хранилищем Clientora. Этот запрос требует обычного входа владельца, CSRF и актуальной `revision` конфигурации.
7. Через `set_mapping` настройте соответствия клиентов и позиций. Существующие заказы могут быть связаны только после проверки администратора; автоматическое обновление такого черновика сначала потребует явного решения о ревизии.
8. Проверьте один заказ в изолированном контуре, затем включите подключение и исходящую отправку на обеих сторонах. В Clientora `automatic=true` добавляет события в транзакцию изменения заказа; `outbound_enabled=true` разрешает их отправку. В ERP используются отдельные `enabled` и `outbound_enabled`. По умолчанию отправка выключена.

Пользователь с ролью `ERP Basic Integration` не может провести или отменить документ даже при наличии стандартной роли Sales User. В режиме ERP Basic ему также запрещены изменяющие HTTP-вызовы общего `erp_basic.api.*`: бизнес-изменения разрешены только через проверяемый контракт `erp_basic.integration.*`. Отдельный сотрудник проводит проверенный черновик обычным интерфейсом ERP Basic или ERPNext.

### Планировщики и адреса

Frappe scheduler вызывает `erp_basic.integration.dispatch_pending` каждую минуту; нужны работающие scheduler и queue workers. По умолчанию обрабатывается не более 20 событий за вызов. В Clientora запланируйте периодический запуск `python manage.py process_erp_exchange --limit 20` существующим планировщиком. Несколько процессов безопасно конкурируют за постоянные резервирования событий.

Рабочие адреса требуют HTTPS, стандартного порта и конечного URL без перенаправлений. Внутренний IP разрешается только явной настройкой `erp_basic_exchange_allowed_hosts` в Site или `CLIENTORA_ERP_ALLOWED_HOSTS` в Clientora. Локальный HTTP предназначен для изолированных тестов: `erp_basic_allow_local_exchange=1`; в Clientora дополнительно нужны `DEBUG=1` и `CLIENTORA_ERP_ALLOW_LOCAL=1`. Сетевое окружение оператора должно разрешать только необходимые получатели.

## Контракт версии 1

Оба приёмника получают JSON с единственным верхним полем `envelope`. Frappe возвращает результат внутри `message`; Clientora использует такую же оболочку для машинного ответа. Вход ERP использует `Authorization: token <api_key>:<api_secret>`, вход Clientora — `Authorization: Bearer <callback_token>`.

| Поле envelope | Значение |
| --- | --- |
| `schema_version` | Целое число `1`. |
| `message_id` | Стабильный UUID сообщения; сохраняется при каждом повторе. |
| `source`, `source_tenant` | `clientora` и UUID Organization, либо `erp_basic` и Connector.local_tenant. |
| `event_type`, `object_type` | `order.proposed`, `order` из CRM; `document.state_changed`, `order` из ERP. |
| `object_id` | UUID заказа Clientora. |
| `object_version` | Положительная целая версия снимка в своей стороне обмена, до 2 147 483 647. |
| `occurred_at` | ISO 8601 с часовым поясом. Время используется для журнала, не для выбора победителя конфликта. |
| `correlation_id`, `causation_id` | UUID цепочки и исходного события; causation может быть null. |
| `payload` | Разрешённые поля одного из двух направлений. |

Входящее `order.proposed.payload`:

```json
{
  "customer_id": "11111111-1111-4111-8111-111111111111",
  "branch_id": "22222222-2222-4222-8222-222222222222",
  "currency": "RUB",
  "delivery_date": "2026-12-15",
  "items": [
    {"offering_id": "33333333-3333-4333-8333-333333333333", "quantity": "2"}
  ],
  "crm_status": "accepted",
  "quoted_total_minor": 25000
}
```

UUID и дата в примере условные. Разрешено от 1 до 100 строк; положительное конечное количество передаётся десятичной строкой. Лимит сообщения — 200 000 байт. `branch_id`, `crm_status` и `quoted_total_minor` справочные. Системные поля, `rate`, `docstatus`, произвольные DocType, названия складов, расчётные итоги и другие неописанные поля отклоняются.

ERP разрешает соответствия, затем вызывает тот же `erp_basic.commands.save_document(kind="orders", ...)`, что и пользовательский API. Сохранение, native validation, проверка `expected_modified` и идемпотентность проходят в общей транзакции. Служебный SQL изменяет только четыре таблицы транспорта.

Исходящий `document.state_changed.payload` содержит `clientora_order_id`, `sales_order`, `erp_doctype`, `erp_name`, `company`, `docstatus`, `status` и доступные поля `currency`, `grand_total`, `outstanding_amount`, `paid_amount`, `received_amount`, `per_delivered`, `per_billed`. Суммы передаются десятичными строками без пересчёта валют. Тип документа ограничен Sales Order, Delivery Note, Sales Invoice и Payment Entry. После события дочернего документа дополнительно ставится в очередь изменившийся снимок Sales Order.

Clientora проверяет компанию, UUID ERP-контура, UUID своего заказа и тип документа. Учётная проекция хранит отдельный снимок и версию каждого `erp_doctype:erp_name`: поздний счёт не теряется из-за ранее доставленного платежа. Старая версия того же счёта не переписывает новую. Повторное использование общей версии с другим содержимым даёт конфликт. `object_version` обмена Clientora является версией разрешённого снимка заказа; исходная `Order.revision` сохраняется в журнале отдельно.

## Транзакции, повторы и конфликты

Изменение документа и его outbox записываются в одной транзакции. Обработчики `after_insert`, `on_update`, `on_submit`, `on_cancel`, `on_update_after_submit` не выполняют HTTP. Входящий inbox и учётный эффект также фиксируются вместе. Ошибка native validation откатывает бизнес-операцию и её outbox; причина остаётся во входящем журнале.

Перед HTTP worker фиксирует резервирование на 90 секунд. Завершение принимает только тот же идентификатор резервирования. При аварии, истечении резервирования или потере ответа получатель может увидеть сообщение снова; неизменный UUID и хеш позволяют вернуть сохранённый результат без повторного документа. Доставка имеет семантику «как минимум один раз», а не обещание единственного сетевого запроса.

Перед каждой исходящей попыткой ERP повторно проверяет активность служебного пользователя, роль Integration, разрешённую Company и native read **на конкретный документ**. Отзыв доступа переводит событие в `Dead Letter / access_revoked` без HTTP. Сохранённый ответ входящего запроса тоже не обходит текущие права, в том числе при новом message_id с прежней версией объекта.

| Состояние | Значение и действие |
| --- | --- |
| `Pending`, `Sending` | Событие сохранено или временно зарезервировано обработчиком. Это ещё не подтверждённая доставка. |
| `Sent` / `Applied` | Получатель подтвердил конкретный UUID / применил входящий снимок. |
| `Stale` | Более новая версия уже известна либо администратор явно оставил ERP; обработка подтверждена без перезаписи. |
| `Needs Mapping` | Настроить соответствие клиента или позиции, затем повторить тот же входящий UUID. |
| `Conflict` | Изменилось тело того же UUID/версии, учётная ревизия или связь документа. Нужна проверка человека. |
| `Rejected` | Входные данные не прошли разрешённую схему или native validation. Исправить причину; смена бизнес-содержимого требует новой версии и UUID. |
| `Retry` | Временная сетевая/серверная ошибка; следующая попытка запланирована. |
| `Dead Letter` | Постоянная ошибка доступа, адреса или исчерпаны 8 попыток текущего цикла; нужен управляемый повтор после исправления. |

Задержка повторов растёт от секунд до часа с небольшим разбросом. Ручной повтор сбрасывает счётчик текущего цикла, сохраняя полный `attempts` и `retry_count`. Изменение содержания сохранённого события не разрешается. HTTP 401/403 требует проверки ключей и прав, 409 — разрешения конфликта, 422 — проверки данных или соответствий; сетевой сбой и 5xx оставляют событие для повтора.

При ручном изменении ERP черновика новая версия CRM не получает автоматически его свежую `modified`. Возникает конфликт. Изменение только `crm_status` или справочной суммы сохраняет метаданные обмена, не переписывая даже проведённый документ. Изменение количества, клиента, валюты или даты проведённого заказа отклоняется.

## Журнал и управляемое восстановление

Методы ERP вызываются как `/api/method/erp_basic.integration.<method>`. Все операции проверяют Company и доступ к подключению; административные действия дополнительно требуют администратора ERP Basic.

| Метод | HTTP и параметры | Результат / права |
| --- | --- | --- |
| `journal` | GET: `company`, необязательные `connector`, `start=0`, `page_length=50` (до 100) | Отдельные `incoming` / `outgoing`, `*_total`, `*_has_more`, общие `has_more`, `can_retry`, `can_manage_mappings`. Одна и та же позиция страницы применяется к каждому направлению. Администратор видит свои разрешённые подключения; сервис — только назначенные ему. |
| `set_mapping` | POST: `company`, `connector`, `external_type`, `external_id`, `erp_doctype`, `erp_name` | Администратор; типы `customer`, `offering`, `order`. Уже обработанный объект нельзя перепривязать к другому учётному документу. |
| `retry_inbox` | POST: `company`, `name` | Обработать исходное сохранённое событие после исправления причины; тот же успешный UUID возвращает прежний результат. |
| `retry_outbox` | POST: `company`, `name` | Состояние `Pending`, а не обещание доставки. `Sent`/`Pending` не дублируются; активная обработка даёт 409. |
| `resolve_conflict` | POST: `company`, `name`, `decision`, `expected_modified`, `reason` | Администратор; актуальная ревизия и причина 8–300 символов обязательны. |
| `reconcile` | POST: `company`, `connector`, `idempotency_key`, необязательные `after`, `limit` | Повторно поставить снимки связанных Sales Order в обычную очередь; до 100 за запрос. Ответ `queued`, `next`. Повтор тех же параметров и ключа не создаёт новые события. |

`resolve_conflict` поддерживает `keep_erp`: оставить учётные значения, пометить входящий снимок как Stale и отправить результат обратно. `rebase_draft` разрешает повторное применение исходного сообщения к **проверенному текущему черновику**. Проведённый документ этим решением изменить нельзя. Решение, причина и отпечаток запроса остаются в результате inbox; одинаковый повтор возвращает это решение, другое решение под тем же подтверждением отклоняется.

Журнал ERP Basic не возвращает payload или ключи. У строки есть `can_retry` и `action`: `configure_mapping`, `review_conflict`, `retry`. Интерфейс показывает сохранённое состояние, причину и реальную серверную попытку. Настройка соответствий и явное разрешение конфликтов доступны через административные методы/Desk; отдельного редактора соответствий в Basic UI пока нет.

В Clientora доступны журнал `GET /api/erp-exchange`, проекция `GET /api/erp-exchange/projection`, `POST .../queue`, `POST .../retry`; в каждом запросе передаётся `org`. Управление требует membership owner/admin и видимости заказа/филиала, конфигурацию меняет только owner. Обычный CSRF сохраняется; исключение применяется только к машинному callback с отдельным Bearer token.

## Резервное копирование, сверка и миграция

Копируйте БД вместе с файлами, ключом шифрования Frappe Site и действующим ключом шифрования Integration в Clientora. После восстановления **до запуска scheduler/worker** включите `erp_basic_disable_external_calls=1` и `pause_scheduler=1` в ERP, `CLIENTORA_ERP_EXCHANGE_PAUSED=1` в Clientora. Восстановленная очередь сохраняет старые UUID; смена UUID для обхода неопределённого результата недопустима.

Проверьте текущие права служебных пользователей, идентификаторы контуров, ключи и соответствия. Сопоставьте исходящие и входящие журналы, затем используйте штатные повтор и `reconcile` для Sales Order. Процедура сохраняет бухгалтерские документы. Автоматическая полная сверка всех исторических счетов и платежей отдельным backfill в эту версию не входит.

Демонстрационные записи ERP Basic переносятся только общей контролируемой миграцией проекта: предварительная проверка, явные соответствия, журнал и проверка результата. Тестовые UUID, пользователи, временные пароли и заказы сквозного сценария не импортируются в рабочий Site. Скрипт тестов явно требует изолированную среду; наличие успешного E2E не означает подключения production Clientora.

## Проверки и воспроизведение

Поддерживаемый проверенный набор: Frappe **15.126.0**, ERPNext **15.124.5**, MariaDB **10.11.19**, Redis **7.2.17**, PostgreSQL **17.11**, Django **5.2.18**. Точные upstream commit и результаты находятся в `docs/clientora-exchange-verification.json`.

На тестовом Site с `allow_tests=1`:

```bash
bench --site <test-site> migrate
bench --site <test-site> execute erp_basic.tests.test_integration.run
```

Проверки используют настоящую MariaDB: native цены, откат бизнеса и outbox, отсутствие соответствия и повтор, конфликт ревизий, запрет изменений проведённого документа, явное сохранение ERP, дубли/старые версии, текущие Company/Customer User Permissions, отзыв служебных прав до HTTP.

В изолированном окружении Clientora с PostgreSQL:

```bash
python manage.py migrate
python manage.py test crm.test_erp_exchange crm.test_integrations --noinput
python manage.py makemigrations --check --dry-run
```

Конкурентные проверки используют PostgreSQL: шесть параллельных одинаковых callback, шесть конкурирующих захватов очереди, атомарный откат, неправильный учётный контур в Stale ACK, поздний счёт после более нового платежа, реальный отказ соединения и запрет отправки после восстановления. В suite также входят существующие проверки других интеграций Clientora.

Скрипт `tools/erp-basic/verify-live-exchange.py` находится в **репозитории Clientora**. Он запускает настоящий Django HTTP-сервер, использует работающий HTTP Frappe и обе БД. Параметры и полный порядок запуска описаны в companion `docs/erp-exchange.md`. Подтверждены обычный вход CRM/CSRF и создание заказа, собственная цена ERP и native submit отдельным сотрудником, обратный callback, дубли и конфликт тела, нарушение порядка событий, потерянный после commit ответ и повтор без второго документа, отсутствие обменного цикла и выдуманного платежа.

Файлы конфигурации E2E содержат временные ключи и создаются с правами 0600. Они остаются вне репозитория. Публичный отчёт не содержит идентификаторов тестовых заказов, реквизитов, адресов частных систем или ключей.

## Границы текущей реализации

Это рабочий обмен заказами и учётными результатами, а не универсальная двусторонняя синхронизация всей ERP. Автоматическое создание справочников, входящий импорт платежей/складских движений из CRM, конвертация любых заданий Clientora Pro в учётные документы, полный backfill исторических счетов и отдельный экран конфигурации в Clientora пока не реализованы. Они требуют самостоятельного контракта, владельца полей и приёмочных сценариев. До этого существующие данные и текущие права имеют приоритет над неподтверждённым внешним сообщением.
