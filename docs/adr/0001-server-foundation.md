# ADR 0001 — ERP Basic как приложение Frappe над ERPNext

Дата: 2026-11-05. Статус: принято; фактическая проверка описана в [отчёте](../verification.md).

## Исходное состояние

В `main` до этой работы находилась самостоятельная демонстрация `dist/`: HTML/CSS/JavaScript, `localStorage['erpbasic-v2']`, JSON schema 2, семь Node-тестов. Сохранение, «проведение», остатки и сумма «к оплате» рассчитывались в браузере. Переключение ролей, обмен Clientora, подписка Business и переход в ERPNext не являлись серверными операциями. GitHub Pages продолжает публиковать только эту демонстрацию.

## Решение

Добавлено отдельное приложение `erp_basic`; интерфейс `/erp` обращается к Frappe API и стандартным документам ERPNext. Файлы ядра Frappe и ERPNext не изменяются. В собственных DocTypes хранятся только идемпотентность, аудит, транспорт обмена и история миграции. Складской и финансовый учёт ведут штатные `Stock Ledger Entry`, `GL Entry`, `Payment Ledger Entry` и контроллеры документов.

Серверный интерфейс использует существующие стили и обе темы. Общие ресурсы синхронизируются `инструменты/синхронизация-стилей.py`; демонстрационный JavaScript в серверную страницу не включается. При ошибке API нет переключения на локальные данные.

## Границы данных

Независимый клиент системы получает отдельный Frappe Site, базу, конфигурацию, секреты и каталоги файлов. `Company` — юридическое лицо внутри Site. Несколько Company допустимы для группы одного клиента. Номенклатура, клиенты, поставщики, контакты и адреса в таком Site являются общими справочниками. Их нельзя использовать для хранения независимых SaaS-клиентов с обещанием отдельной приватности.

Обычному пользователю нужны стандартная роль ERPNext и явный `User Permission` на Company с `apply_to_all_doctypes=1`. Отсутствие Company-разрешения означает отказ. Site Administrator / System Manager управляют всем своим Site. Организация Clientora сопоставляется с одним connector и Company; входящий `source_tenant` сам по себе не даёт доступа.

В Basic открыт небольшой перечень HTTP-команд. Стандартный `/api/resource` для обычных пользователей предоставляет ограниченное чтение известных DocTypes с проверкой Company; запись и document RPC проходят через типизированные команды Basic. Произвольные отчётные RPC, batch-вызовы и незнакомые методы закрыты. Это необходимо, поскольку не каждый стандартный отчёт ERPNext строится через `get_list` и наши query conditions. Администратор сохраняет штатный Desk для настройки. Приватные файлы дополнительно проверяют доступ к документу-родителю.

## Транзакции

Успешный POST фиксирует Frappe; необработанное исключение откатывает запрос. В одной транзакции находятся документ, native движения, запись команды, бизнес-аудит и outbox. В прикладных командах нет ручного `commit`.

Ключ команды scoped по Site, Company, пользователю и операции. `ERP Basic Operation` хранит SHA-256 канонического запроса и результат. UPSERT и `SELECT FOR UPDATE` сериализуют конкурентные повторы. Совпавший ключ с другим телом даёт 409; перед возвратом сохранённого ответа заново проверяются текущие права. Новые ключи не разрешают повторно провести тот же native документ.

Изменение существующего документа требует `expected_modified` и блокирует его строку перед повторной проверкой версии. Для складских операций дополнительно блокируются Item в одинаковом порядке; это защищает и первое движение до создания Bin. MariaDB должна работать с `READ-COMMITTED`: ожидающая операция получает актуальное состояние после commit соседа. Проведение отказывает при другой изоляции.

Внешняя HTTP-доставка выполняется worker после commit. Durable outbox, lease и повтор одной envelope позволяют восстановиться после остановки процесса. У получателя inbox и бизнес-эффект фиксируются атомарно. Нельзя считать один `after_commit` callback очередью гарантированной доставки.

## Учётная политика Basic

Используется `Moving Average`, отрицательный фактический остаток запрещён. Операции вызывают штатные `.insert()`, `.save()`, `.submit()` и `.cancel()`. SQL не исправляет GL/SLE. В Basic нельзя включить отрицательный остаток на отдельном Item или выбрать другой метод оценки; изменение политики при переходе в полный ERPNext требует отдельной проверки.

Физическая отгрузка — Delivery Note; начисление задолженности — Sales Invoice. Созданный по отгрузке счёт имеет `update_stock=0`. Аналогично Purchase Receipt и Purchase Invoice. Дублирование складского эффекта по связанной накладной запрещено дополнительно в DocType hook. Сумма Sales Order, аванс по заказу, задолженность по счёту и подтверждённая оплата показываются как разные показатели.

API принимает десятичные строки, проверяет конечность и диапазон, затем передаёт значения в числовые типы и правила точности ERPNext. Денежные поля возвращаются с native точностью; базовая настройка валюты — 2 знака, количеств — 6. Валюта нового документа берётся из выбранной Company. Для платежа отдельно возвращаются валюты обоих счетов. Browser не пересчитывает проводки или итоговые суммы.

Бизнес-даты относятся к часовому поясу Site, по умолчанию `Europe/Moscow`, и приходят из `session.business_date`. `modified` — непрозрачная версия native документа. Интеграционные события имеют время UTC с явным offset. При установке в другом часовом поясе настройку меняют до ввода документов.

Задние даты, дополнительные расходы, пересчёт последующих движений, закрытие периода и возврат по исходной стоимости принадлежат ERPNext. Очереди repost должны обслуживаться worker. Основные тесты включают возвраты, отмену, конверсию UOM и стоимость; сложные партийные/серийные сценарии и ретроспективная массовая переоценка не объявлены испытанными. Отдельной команды физического резервирования в интерфейсе Basic пока нет; отображаемые резервы — штатные показатели ERPNext.

## Перенос и расширение

JSON v2 не содержит достоверной истории всех складских и банковских фактов. Поэтому выбран начальный срез: native справочники, Stock Reconciliation, отдельно проверенный финансовый opening Journal Entry и неизменяемый архив старых документов/связей/history. Исторические движения не складываются с конечным остатком. Исходные черновики предложений и заказов переносятся в native черновики; открытые строки частично исполненных старых заказов требуют сверки. Подробности — [миграция](../migration.md).

Переход к полному ERPNext использует те же Company, Item, документы и регистры. Флаг `erp_basic_full_erpnext` открывает стандартные RPC после проверки новых ролей; он не мигрирует и не перепроводит данные. Проверка сохранения ID и записей регистра включена в контрольную миграцию. Это проверка общей модели; включение производства, дополнительных модулей и новых ролей остаётся отдельным внедрением.

## Альтернативы и последствия

Отдельный Django/FastAPI backend позволил бы повторно использовать технологии Clientora, но потребовал бы собственного учётного ядра, складской оценки, прав и последующего переноса в ERPNext. Подтверждённого ограничения Frappe для текущего объёма нет. Форк ERPNext создавал бы ненужное сопровождение; вместо него используются app hooks и native контроллеры. PostgreSQL Clientora не определяет выбор СУБД ERPNext.

Цена выбранного решения — эксплуатация Frappe/ERPNext, Redis и worker, знание их обновлений и повторная проверка при смене версии. Нужны отдельные Sites, резервное копирование полного комплекта и проверка восстановления. Версия PHP/микросервисы/дополнительный брокер для этого этапа не добавляются.
