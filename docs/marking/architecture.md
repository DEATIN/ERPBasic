# Решения и контракт маркировки

## Переиспользование

| Уже существовало | Расширение |
|---|---|
| Frappe Site/Company, сессии и роли | Роли оператора и менеджера; повторная проверка источника, Item/Warehouse перед ответом и командами |
| Native ERPNext документы/SLE/GL | Guard связывает конкретную строку с подготовкой; нового складского или финансового регистра нет |
| ERP Basic Operation | Те же транзакционные idempotency keys; добавлена дедупликация отдельных событий сканера |
| Browser PendingStore | Один неподтверждённый запрос на обычный ERP и маркировку; отдельная последовательная очередь сканов |
| ERP Basic Outbox/Inbox для CRM | Компактные проекции v2, без изменения версии native событий v1 |
| Backup/restore | Одиннадцать таблиц маркировки, потоковый checksum, расшифровка КМ и исходные идентификаторы |

## Данные и инварианты

`Setup` хранит несекретный паспорт и выбранный фискальный контур. `Product` связывает Company/Item с GTIN, профилем и режимом контроля. `Job` хранит до 100 товарных строк и максимум 100 000 ожидаемых единиц; сырые сканы не помещаются в child table документа.

`Code.name` — SHA-256 канонической идентичности GS1 AI01+AI21 в пространстве Site, без Company. Поэтому перевод между Company не может создать две независимые активные копии. Автоматический перевод принадлежности между Company не реализован; конфликт требует отдельной согласованной процедуры. Company здесь задаёт область хранения/ответственности ERP, а `regulatory_owner` — отдельное неподтверждённое поле.

Исходный скан шифруется ключом Site. Отпечаток нормализованной строки позволяет заметить другой криптохвост у того же КИ; он не считается новым экземпляром. Синтаксический разбор не проверяет криптографическую подлинность.

`Scan` хранит принятые/отклонённые события. Его устойчивое имя для устройства включает Company, пользователя, device_id и event_id. `Device` ведёт монотонную последовательность по заданию. Ожидаемый список поставщика хранится отдельно в `Expected`. `History` — неизменяемый журнал бизнес-переходов; полный КМ в него не попадает.

`Package` — внутреннее дерево с версией, одним родителем и историей. Оно не выдаёт SSCC и не утверждает регуляторную агрегацию. `Operation` — отдельная очередь регуляторного намерения, пока только с тестовым адаптером. `Import` фиксирует source_id/external_id/hash контрольного переноса без plaintext исходной строки.

Контроллеры закрывают прямую запись/переименование/удаление. Native HTTP, DocShare и File-пути не открывают исходные коды. ERPBasicFile — узкое наследование штатного File: проверка источника до копирования и проверка области до чтения содержимого, включая ZIP.

## Транзакции и блокировки

HTTP-команда фиксирует локальное состояние и результат идемпотентности одной транзакцией. Сетевых ожиданий в ней нет. Скан сначала сериализует событие, затем задание, затем экземпляр. Первое появление экземпляра использует INSERT/unique name/FOR UPDATE, поэтому два процесса не получают два резерва.

Создание/завершение задания с основанием согласовано с native документом. Порядок native основание → маркировочное задание исключает появление Prepared между проверкой native submit и его on_submit. Открытое задание блокирует проведение основания; одна строка не может одновременно подтвердить две партии. Перед физическим приходом заново проверяются количество, исходное состояние и сопоставление товара.

Внутреннее дерево упаковок изменяется под общей блокировкой Company. Это намеренно консервативное решение; производительность массовой агрегации на миллионе КИ не измерена. Все package mutations увеличивают версию задания и закрыты при внешней операции, кроме подтверждённого отказа.

Worker фиксирует аренду перед вызовом адаптера. Неизвестный результат или истечение аренды переводят Operation в Unknown, без освобождения бизнес-резерва. Сверка использует прежний business_key. Поздний результат не перезаписывает попытку с другим lease_token. Никакой «распределённой ровно-однократной фискализации» этот механизм сам по себе не обещает.

## Компактная проекция Clientora v2

Envelope сохраняет поля v1: message_id, source/source_tenant, object_id заказа CRM, occurred_at, correlation_id и causation_id. Новая пара — `schema_version=2`, `event_type=marking.summary_changed`, `object_type=order`.

`object_version` означает **версию job_id**, равную `Job.revision + 1`; она не сопоставляется с глобальной версией заказа или другого задания. Payload содержит clientora_order_id, company, erp_doctype=`Sales Order`, erp_name/sales_order и объект marking:

- job_id/job_version, роль, намерение, локальный этап;
- профиль/версия/режим, test_only и Preparation/Test;
- ожидаемое/принятое количество, проблемные события и до 100 товарных строк с reference_line;
- неизменные fiscal_owner/sale_id;
- external_state=`Unverified`, пустые время/источник внешнего подтверждения и коды блокировок.

Ни КИ/КМ, ни криптографические части, ни команда чека не передаются. Создание задания и смена его этапа атомарно добавляют снимок в существующий Outbox. Для явной сверки есть `queue_projection`; обычные сканы не засоряют обмен тысячами промежуточных сообщений.

`marking_enabled` по умолчанию выключен, `marking_endpoint` задаётся отдельно от endpoint v1. Доставка повторяет прежний message_id и payload; текущие права служебного пользователя и основания проверяются перед отправкой. После restore исходящий обмен и внешние вызовы выключены.

`outbound_enabled` остаётся общим выключателем исходящего обмена Connector для обеих версий. `marking_enabled` разрешает создание проекций v2, но при выключенном общем обмене они остаются в очереди. Для доставки нужны оба флага и снятый оператором Site запрет внешних вызовов. Это позволяет подготовить проекции до включения транспорта и сохраняет изоляцию restore.

Получатель должен иметь существующие ERPOrderLink и подтверждённый erp_reference. Если v2 обогнал первый v1, оператор сначала завершает сопоставление; проекция не подменяет соответствие заказа. Получатель хранит хеш/версию по job_id, учитывает старые/повторные/конфликтующие сообщения и проверяет текущую область до cached ACK. Успешная проекция не вызывает Order.save, ledger, fiscal commands или обратный outbox.

## Этапы, которые нельзя считать завершёнными

Подписанные payload, реальные квитанции НК/СУЗ/ГИС МТ/ЭДО, физическая печать/перепечатка, сертифицированный кассовый мост, offline-разрешение и фискальные чеки требуют адаптеров выбранных поставщиков. Их endpoints, лимиты, алгоритмы подписи и схемы не заменены догадками. Подготовленные интерфейсы являются местом расширения, а не доказательством промышленной совместимости.

Полномасштабные 10 000 SKU/1 млн КИ/задание 100 000, независимые автономные кассы, временные сертификаты/МЧД и сравнительный пользовательский пилот не проверены. Измерения сервиса/БД, браузера и внешних сервисов публикуются раздельно.
